Rebound

rzp-rebound

A unified revenue-at-risk engine for Razorpay. Three detectors sweep an account for money that is owed and not collected, the queue collapses the sightings that are the same debt, a fifteen-rule policy gate decides one action per item, and an intervention engine executes only what the gate allowed. Every decision is an append-only audit row carrying the rule id that produced it, including the refusals.

What this is. The committed artifacts of one run against Razorpay test mode on 2026-09-05: the seeded book, the run summary, every result row, the audit ledger, the escalation queue, and the two snapshots taken around a payment. They are files compiled into this binary. Serving them calls no gateway.

The seeded book

What cmd/seedbook created in the test-mode account before the run: invoices at four age buckets and abandoned orders, with per-item flags. Ages are the manifest's own, not Razorpay's, because no call in the invoice or order API can backdate a resource. Every row the run wrote says which clock it used.

Sightings, then items

Razorpay mints an order when an invoice is issued, so one debt is reachable from two detectors under two ids. The queue collapses on the root order rather than on the sighting, or the customer is contacted twice about one debt.

Verdicts by rule

First match wins, three verdicts, one decision per item. An escalating verdict raises a second decision, on the escalation itself, which goes through the same gate: the kill switch stops handing an item to a person the same way it stops everything else. Those are counted separately below, so the allow count never exceeds the number of items.

The audit ledger

Append-only JSONL, one row per decision, refusals included. policy_evaluated goes down before anything acts on it, so a denial leaves the same trail an allow does.

No live gateway sits behind this page. The replay view serves committed files from one run against Razorpay test mode. The run view drives a fixture book through a simulated in-memory gateway. This process holds no Razorpay credential, reads no key from its environment, and never constructs a gateway client.

A paid transition observed in the replay is n=1, paid by the person running the demo, and selected rather than sampled. Nobody decided independently to pay. It is not a sample of anything and no recovery rate is quoted off it. An accepted notification means the notification API call succeeded, never that a person read anything.

A test-mode number is not evidence about real customers. HONEST-LIMITATIONS.md is the full list, and it is longer than this footer.
